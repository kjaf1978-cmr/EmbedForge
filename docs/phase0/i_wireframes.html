EmbedForge — Phase 0 (i) UI wireframes

BaselineEmbedForge_prompt_v3.5 (section 12, UI-01..UI-23) Version0.1.0 Date2026-10-05 Prepared bybuilder (Claude) Statusdraft Human review record (DOC-12)pending

These are low-fidelity wireframes. They fix what each view contains, how views link to each other, and which states must be visible. They do not fix visual design, exact spacing, icons or colours. Grey boxes are placeholders; the one accent colour marks the current selection and cross-highlighted artefacts (UI-02).

Example project in every wireframe: ACC-02 on an ELEGOO UNO R3 (PCB build, Uno shield, module part style). Signals: A, B analog in; C, D, E digital in; U, V digital out; W analog out by PWM + RC filter (no DAC on the Uno, ACC-02 Q8); counter output P on a PWM pin; DC motor via a TB6612FNG module with a separate supply. The pin assignment, requirement numbers and parameter values shown are illustrative placeholders chosen to be plausible on the Uno; the real values come from ED-01 and the clarification answers.

Project state assumed in the wireframes (unless a frame says otherwise): status Designed (ST-03); all automated gates pass, so the project is Verified-auto (ST-09); VER-06 is not yet passed only because the DOC-12 human review records are missing, so status Verified is not claimed. Generated code carries the Code verified label (INV-06), which is shown separately from the project status. Four HIL checklist items are HIL-pending (ST-08).

HIL-pending (ST-08)
HIL-03 U LED visible at A = B on hardware HIL-pending
  1. Controls: start, pause, step (step size selectable), speed; the emulated-to-real-time ratio is always visible in the toolbar and status bar (EM-06). If the host cannot keep up, the ratio drops below 1× and timing stays correct (time-accurate).
  2. Instruments: virtual multimeter, oscilloscope, logic analyser, serial monitor, serial plotter, pin-state panel — each is a dockable widget; probes are attached by clicking a net in the animated breadboard.
  3. Users drive inputs interactively (sliders, buttons; temperature/joystick widgets appear when such parts exist) and run scripted scenarios with expected outputs; scenario results feed VER-05.
  4. Every part without a qualified model shows not emulated on the breadboard, in pin states and in widgets (EM-08); requirements depending on it show HIL-pending.
  5. Cross-highlight: selecting R3 highlights sliders A, B, LED U, pin rows A0, A1, D8 and scenario EMU-SC-03.

Why not Verified?
Status Verified needs the DOC-12 human review on each document (ST-09). Open review checklist
  1. Matrix of every gate per requirement, columns limited to gates of the project’s build style (PCB here; perfboard shows VER-14, breadboard VER-15). Each cell drills down to evidence: logs, inputs, versions.
  2. Project status stepper shows all six ST-01 states, the current one, and exactly what blocks the next one. Verified-auto is displayed separately and never labelled “Verified” (ST-09).
  3. HIL items show HIL-pending until a result is recorded (ST-08); recording opens the DOC-07 result form.
  4. After any change (ST-07) cells turn “stale” (outlined, not ticked) until gates re-run; status drops to the highest still-valid state.
  5. Code verified label and its gate list (INV-06) are shown next to, not inside, the status.

Expert mode differences
Navigator, all views and splits always available; no stepper; every function in menus.

Switching keeps the selection, open views and undo history. Guided mode hides no state: the status bar is identical.
  1. Guided mode is a six-step stepper: board → describe → clarify → review → emulate → build. A step is unlocked when the previous one’s exit condition holds (e.g. Clarify needs INV-12).

  3. Edge case: switching to guided mode on a project that is already Designed puts the user on the furthest unlocked step.
